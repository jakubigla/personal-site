## Constraint
The site is available 99.5% of each calendar month. A bad release is undone by reverting its commit on main and letting the normal deploy publish the previous version, within 1 h of the decision to roll back.

## Acceptance
- AC1: The availability target is 99.5% per calendar month (at most about 3 h 39 min unavailable), measured from CloudFront's default 5xx error-rate metric with no paid probe.
- AC2: Reverting a release's merge commit on main and letting the deploy pipeline (FR-025) run puts the previous version live within 1 h of the decision to roll back.
- AC3: Rollback needs no console step, no S3 object versioning and no manual file copy; the deploy pipeline is the only path.
- AC4: The runbook in the repo describes the revert-and-redeploy rollback step by step, next to the cut-over rollback from NFR-022.

## Notes
The PO chose revert and redeploy over S3 versioning or per-release prefixes because content history already lives in git, so a sync with delete is acceptable. No uptime probe exists (Q6), so availability is read after the fact from CloudFront metrics. The PO did not place this in the MVP, but it costs nothing beyond FR-025 and the runbook.
