## Outcome
The GitHub settings setup made by API are Terraform, imported as they are, a stack that reuses the platform's state backend (its own key) and Terraform conventions, never a store of its own, checked statically by CI per PR with no credential (ADR-0010), planned and applied by the PO locally.

## Acceptance
- AC1: after the owner pins and renders the foundation, xpm init foundation status answers step rendered or later; deferred stays true by design under ADR-0010
- AC2: The first github plan imported the live settings and changed nothing on GitHub
- AC3: A pull request touching foundation/github gets a github-config workflow run that executes only terraform fmt, validate and the static policy checks, with no cloud credentials
- AC4: xpm doctor's github-as-code row shows only the states ADR-0010 leaves: `info` (settings set by API) before the owner renders the foundation, and `warn` naming the step it stopped at (stopped at `rendered` or later) after the render; `ok` is not reachable by design, since doctor's `ok` needs step `vars-set`, which needs a CI plan identity (ADR-0010, A-021) (EN-011 AC4, reworded to fit ADR-0010)
