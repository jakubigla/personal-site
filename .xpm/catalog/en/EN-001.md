## Outcome
Stand up the static site build with the framework chosen at architecture, and the single structured content file with its schema and section flags, so one value travels from the content file through the build into a plain static HTML page. The skeleton renders a minimal hero and footer from the content file, honours a section flag, and ships with the reserved, flagged-off "How I deliver" slot, giving every later section a place to plug in without touching layout code to change a fact.

## Acceptance
- AC1: A single build command produces a directory of plain static files (HTML, CSS, assets) with no server runtime needed to serve them.
- AC2: The content file is validated against its schema during the build, and an invalid file (missing required field, unknown section flag) fails the build with a readable error.
- AC3: Changing the headline text in the content file and rebuilding changes the rendered hero without any edit to layout code.
- AC4: Turning a section flag off in the content file removes that section from the built HTML; the "How I deliver" flag exists and is off by default.
- AC5: The built page is readable top to bottom with JavaScript disabled.
- AC6: A local test run (unit or build check) passes against the skeleton.
- AC7: Foundation (outcome): the seat writes the repo's CI, task runner, hooks and dependency-update
  config for this stack itself (practice xpm/foundation-sized-to-project), every version from
  `xpm latest`, each tool configured once. Proven by running it, on the PR:
  - the documented command (README.md `## Run locally`) runs the stack on a clean clone;
  - CI runs on the PR and publishes the one required check `ci-ok`, green;
  - the secret scan runs: `.pre-commit-config.yaml` lists xpm-sensitive-scan and
    xpm-sensitive-scan-push, `xpm init hooks` installed them, and `pre-commit run --all-files`
    passes over every file, old files included;
  - dependency updates are configured for every ecosystem the repo uses, GitHub Actions included;
  - the exercising profile (`xpm paths committed surfaces`, shaped like
    `$(xpm root)/docs/exercising.example.md`) names every surface the ACs run on, and
    `xpm exercising_profile.sh validate` exits 0;
  - runtime versions the brief or an NFR names (none) are the ones the project pins.
- AC8: Foundation (judgment): for each component web and infra, the module layout, the first ADRs, the
  import boundaries and how much CI it gets follow its tier and its blueprint's knowledge, if it
  has any: read every file `xpm blueprint knowledge --paths` prints (each component's
  blueprint notes for its stack and tier, plus `repo`'s, which bind every component).
- AC9: Local run: one documented command starts the whole stack locally, verified on a clean clone
  of main with nothing exported: whatever a fresh clone needs (installs, a non-secret local value
  for every variable the app reads, synthetic data only - no real or personal data) comes from
  the documented steps, never a README-only `export`. README.md's `## Run locally` section gives
  those steps in order, every loopback URL the stack serves and how to stop it. The local-run
  check runs the recorded tasks on a clean clone and probes each loopback URL in the section body
  (to its first `###`), https with no certificate check: another stack's URL goes under a `###`.
  The tasks are `mise run web:install` (setup), `mise run web:dev` (start, serving
  http://localhost:4321) and `mise run web:test` (tests).
- AC10: Main regression: .github/workflows/ci.yml runs the full test suite, Playwright included, on every pull request and every push to main, in job web (ADR-0016); the deploy job needs it.
- AC11: The skeleton follows the module map and walking skeleton of docs/architecture.md: apps/web (Astro, content/en.yaml with its Zod schema) and an infra root that passes fmt, validate and tflint with no cloud credentials; the deploy job exists and is skipped while the deploy role variable is unset.

## Notes
Framework and content format are decided: Astro with TypeScript and CSS custom properties (ADR-0002), one YAML file per language validated by Zod (ADR-0003). Components and tiers: web (standard), infra (starter) (ADR-0001). Selected-work entries use anonymized labels only; no real client name may enter the content file or any fixture.
